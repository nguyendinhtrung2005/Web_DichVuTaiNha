# Customer API integration

Customer now chooses cash/transfer during both service booking review and product checkout. Service checkout creates/replays its booking then records the choice with the existing payment-simulation API before completion; a Payment failure keeps the original request for recovery. Product checkout sends `paymentMethod` with the purchase journal, and list/detail pages show the server-derived simulated payment state. Legacy orders show no invented choice; product checkout requires migration 004. See [checkout payment contract and verification](../../backend/docs/customer-checkout-payment.md). No real bank transfer or PAID confirmation is implemented.

The approved price-confirmation update sends `expectedUnitPrice` with a booking and with each product-order item. This is compared against server prices, never used as an authoritative price. A price change keeps the form/cart, reloads the current price and requires another explicit confirmation with a new request key. Recovery of an uncertain submission retains its original key and payload. New service bookings enforce the current UI start slots in Vietnam time. Deploy/restart Customer and backend together; legacy clients without confirmation cannot create new orders. No migration or new environment variable is needed. See [Customer flow corrections](../../backend/docs/customer-flow-corrections.md) for the approved contract and legacy recovery rules.

Customer always uses the gateway API; unavailable backend/database responses are shown as errors and never replaced by demo data. Staff and Admin retain their existing independent browser demo behavior.

Copy `apps/customer/.env.sample` to `apps/customer/.env.local`, then set `NEXT_PUBLIC_API_URL` to the gateway public base, such as `http://localhost:4000/api/v1`. This public variable contains no credential and is fixed at build time. Restart development or rebuild after changing it. Configure the gateway allowed Customer origin to match the browser URL exactly (`http://localhost:3001` locally); use the same hostname consistently for frontend and gateway.

From `frontend`, install dependencies and run `npm.cmd run dev:customer`. Start backend with the backend README instructions. Customer loads real catalog rows and owned account/orders/payments/reviews using `{data: ...}` responses from the approved contract at `backend/docs/customer-api-contract.md`. Collection responses must be paginated `{items,total,page,limit}`.

Login accepts phone or email. Registration requires name, phone and password, with optional email. The additive email migration is a separate database owner step and is never run by the frontend. Passwords and bearer tokens are never stored in localStorage or sessionStorage. The browser sends the HttpOnly session cookie with `credentials: include`.

Profile updates support name, phone and optional email. Avatar upload and address editing are disabled with an explanation because the existing schema/API does not support these changes. Existing addresses can be displayed; booking still accepts its own contact/address. Reviews submit one rating and a comment for a completed order with an assignment. Payment operations are explicitly simulations; they never confirm receipt of money.

The Customer cache exists only in memory and refreshes after mutations, navigation, window focus and every 30 seconds while the page is visible. A 401 clears owned data and asks the user to sign in again. Existing `cleanhome-demo-state-*` keys are preserved and are never used as Customer API authentication or business data.

The service catalog groups legacy services into exactly Vệ sinh, Chăm sóc and Bảo dưỡng while preserving service IDs, URLs and stored booking snapshots. Detailed service metadata comes from Catalog; missing legacy scope/included/excluded data is shown as unavailable rather than fabricated. Customer booking sends a UUID idempotency key. After an ambiguous network/server result, the form locks the submitted fields and retries the exact same key and payload so Order can return the existing booking instead of creating a duplicate. Additive migration `003_booking_idempotency.sql` was separately approved and applied to the local database on 2026-11-06; other environments require their own approval. Product browsing, detail, the tab-memory cart and product orders use `/catalog/products`, `/catalog/product-categories` and `/product-orders`; these are separate from booking and never add suggested products without an explicit customer action. Checkout requires a signed-in customer but no service date/time. The API revalidates price and stock; `PROCESSING`/`PENDING` does not mean payment or shipping. See `backend/docs/services-products-contract.md`.

Booking forms now keep an account-scoped draft in tab memory across client navigation and temporary session expiry. Re-authentication returns to the requested page. The same account can recover contact/house/schedule/notes and the original uncertain request key/payload. Explicit logout, switching accounts, successful booking or a full page reload clears the relevant personal draft; no browser storage is used. Order pages offer separate service/product navigation and service progress with next-step guidance. Local demonstration data is explicitly labeled `[DEMO]`; see `backend/docs/customer-local-demo.md`.

Logic fixes (2026-11-06): booking paths always identify services; reorder links append `?rebook=orderId` and verify the owned matching-service order before prefilling. Return destinations preserve the query. Session requests capture a security epoch independent of polling; stale responses cannot expire a new session, and Auth401 clears private cache independently of a Catalog outage. Auth acknowledgements remain successful with a warning if business-data refresh fails. Catalog/Order/frontend share fractional-service quantity bounds (`0.01–100000`, at most two decimals); products still require whole units. Product order loading errors and not-found results are separate from a successfully loaded empty list. See `backend/docs/customer-logic-fixes.md` for files and verification.

Product relations, stock reservations and order persistence require additive migration `databases/migrations/002_services_product_orders.sql`. The user separately approved applying this exact migration on local 127.0.0.1:3306 / dich_vu_ve_sinh on 2026-10-30; its five statements and resulting metadata have been verified. It is never applied automatically. Other environments still require their own owner approval; missing migration/API failures are shown to the customer with no mock-product fallback. Setup and user flows are detailed in [SERVICES_PRODUCTS.md](SERVICES_PRODUCTS.md).

Checks: `npm.cmd run typecheck:customer`, `npm.cmd run typecheck:staff`, `npm.cmd run typecheck:admin`, and `npm.cmd run build:customer`. Browser HTTP integration checks must state whether they use actual MySQL or test-only repositories.

Use Case alignment (2026-11-07): service searches/filters send q/group/cleaningType to Catalog. Order/history pages send q/serviceId/status/from/to/sort/page/limit to Order with server pagination. Date filters, booking input and Customer time display use Asia/Ho_Chi_Minh. Rental/family house details are required server-side; phone validation matches Auth. Order detail shows saved unit prices. Review starts without a selected score and retains input after POST failure. Service detail reads public count/average through Review and its read-only Order dependency, without exposing private identity/comments. An ACK followed by reload failure is a warning, not another write. Cancellation remains pending and payments simulated by task-owner confirmation. Evidence and limitations: [Use Case verification](../../backend/docs/customer-use-case-verification.md).
